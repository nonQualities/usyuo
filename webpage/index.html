Abstract & System Overview

usyuo is an in-memory task database, lexical parser, and query engine implemented in C3 for the todo.txt specification. By combining sequential virtual memory arena mapping, cache-line packed task data structures, and integer Julian Day calendar arithmetic, usyuo achieves ingestion throughput of 404,800 tasks/second (0.494s for 200,000 tasks) with zero secondary heap allocations.

1. Architectural Implementation

1.1 Zero-Copy Virtual Memory Arena Runway

Standard text parsers execute separate dynamic heap allocations for individual lines, tokens, contexts, and project tags. usyuo eliminates memory fragmentation and allocator overhead by loading the entire dataset into a single contiguous, 8-byte aligned virtual memory arena (MemoryArena) using a single sequential disk read.

Task lines, context tags (@context), project tags (+project), and task descriptions are represented as 16-byte zero-copy slices (char* ptr and usz len) pointing directly into the arena memory runway. Ingesting 200,000 tasks executes with zero individual heap string allocations.

1.2 48-Byte Cache-Line Aligned Task Structure

The core AST representation of a task is packed into exactly 48 bytes with 8-byte alignment, fitting inside a single 64-byte L1 CPU cache line: 

struct Task {
    int id;              // 4 bytes: Task identifier (1..N)
    bool completed;      // 1 byte : Completion status flag
    char priority;       // 1 byte : Priority marker ('A'..'Z', or 0)
    char[2] _pad0;       // 2 bytes: Alignment padding
    int completion_jdn;  // 4 bytes: Completion Julian Day Number
    int creation_jdn;    // 4 bytes: Creation Julian Day Number
    int due_jdn;         // 4 bytes: Due date Julian Day Number
    char[4] _pad1;       // 4 bytes: Alignment padding
    String raw_line;     // 16 bytes: Zero-copy slice (ptr + len)
    String description;  // 16 bytes: Zero-copy slice (ptr + len)
} // Total: 48 bytes (fits inside 64-byte L1 cache line)

Because each struct occupies less than one cache line, sequential iterations optimize L1/L2 hardware prefetcher bandwidth and avoid cache line split penalties.

1.3 Integer Julian Day Calendar Arithmetic

Calendar date strings (YYYY-MM-DD) are never evaluated via string comparison or regex matching during queries. During lexical analysis, dates are projected into integer Julian Day Numbers (JDN) via the Fliegel–Van Flandern algorithm:

a = ⌊ 14−month 12 ⌋ y = year+4800−a m = month+12⁢a−3 JDN = day + ⌊ 153⁢m+2 5 ⌋ + 365⁢y + ⌊ y4 ⌋ − ⌊ y100 ⌋ + ⌊ y400 ⌋ − 32045

Implemented in C3 using integer truncation division:

int a = (14 - month) / 12;
int y = year + 4800 - a;
int m = month + 12 * a - 3;
int jdn = day + (153 * m + 2) / 5 + 365 * y + y / 4 - y / 100 + y / 400 - 32045;

Temporal validation (e.g., evaluating whether a task is overdue or due on a specified date) reduces to a single 32-bit integer comparison (O(1)): 

if (task.due_jdn != 0 && task.due_jdn <= system_jdn) {
    // Overdue or due today: single CPU clock cycle integer comparison
}

Serialization back to ISO-8601 calendar strings during workspace disk flush utilizes the constant-time Richards–Hatcher inversion algorithm.

1.4 Arena-Backed Inverted & Temporal Indices

Posting lists for context tags, project tags, and due dates are allocated via an 8-byte aligned bump pointer directly inside the memory arena. Index insertion operates as an O(1) linked-list prepend. Querying an arbitrary tag (@backend, +c3engine) performs an O(1) hash lookup followed by an O(K) traversal of posting nodes.

2.4 Contributing & Engineering Standards

Contributions, profiling benchmarks, and bug reports are welcomed via GitHub Pull Requests. Before submitting patches, please review our engineering guidelines:

AI Tooling Policy: We encourage contributors to utilize AI assistants, LLMs, and language models strictly for research, conceptual exploration, and learning. However, do not submit AI-generated code or automated implementations. usyuo is an exercise in manual systems craftsmanship, requiring precise reasoning around cache line alignments, zero-copy pointer lifetimes, and memory arena boundaries. Every line of code submitted must be deeply understood, reasoned through, and hand-written by the contributor.

Validation: All pull requests must pass the test suite and stress benchmark with zero regressions: 

make test    # Runs arena, parser, and sorting unit tests
make stress  # Ingests 200,000 tasks to verify memory runway stability
